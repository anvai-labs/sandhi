# Sandhi 0.18: optional authentication and coordinated identity integration

Status: **unreleased source candidate**. Published Sandhi remains
[0.17.1](v0.17.1.md). Source tests, public CI, publication and deployment are
separate gates; this page does not establish a completed public OIDC deployment.

## Access profiles

| Deployment | Selection | Identity and budget |
| --- | --- | --- |
| Fresh local starter | No auth mode or OIDC configuration; loopback listener | One fixed server-owned identity and shared budget |
| Scoped virtual keys | Explicit `SANDHI_AUTH_MODE=tokens` | Configured key bindings and scopes |
| Browser SSO and agent access tokens | Explicit OIDC mode, or an OIDC configuration without a mode | Verified subject, explicit role and inference grants |

`SANDHI_ADMIN_TOKEN` protects operator actions; it does **not** enable inference
authentication. Select the matching inference profile explicitly for shared
deployments. Invalid configured authentication refuses startup or access and
never retries with a weaker profile. The embedding library retains its existing
default token profile.

The starter retains the original durable owner, both budget legs, cache ownership,
source validation and refusal behavior. Its dashboard displays **Shared starter
access**. It provides no per-person or tenant isolation. Existing quickstart token
profiles remain selected rather than being silently changed to starter access.

## Authenticated listener upgrade

Token and OIDC profiles now require listener TLS. The same rule applies to a
starter with an operator token or client-credentials registry. Configure a trusted
certificate and matching key through `SANDHI_CONFIG`; qualify the hostname and
client trust before restarting. Existing credential-bearing LAN or wildcard HTTP
listeners refuse startup.

For deliberate local tests or same-host TLS termination,
`SANDHI_ALLOW_LOOPBACK_HTTP=1` permits only literal loopback sockets. It does not
authorize LAN plaintext or trust forwarding headers. See the
[listener transport contract](../operator/oidc-sso.md#listener-transport).

OIDC mode rejects ordinary virtual keys retained from token mode. Delegated keys
remain disabled by default and require an explicit Sandhi policy; enabling them
does not reactivate ordinary keys. The dashboard now reflects this distinction
in its mint controls.

## Upgrade checklist

1. Preserve the original ordinary ledger file, provider vault and explicit access configuration.
2. Keep `SANDHI_LEDGER_SHARDS` at one and remove `SANDHI_BUFFERED_ACCOUNTING`.
3. Confirm the selected access profile before starting the candidate. An existing OIDC configuration continues to select OIDC when the mode is omitted.
4. Configure listener TLS for credential-bearing profiles; verify readiness, model routing, a real tool loop, refusal controls and original source/paired receipt joins.
5. Adopt the official 0.18 SDK in Victor only after Sandhi publication and artifact verification; candidate binaries do not establish published SDK acceptance.

The [0.17.1 guide](v0.17.1.md) records the durable execution migration and published
artifact provenance. Existing observations and liabilities remain on that original
ledger; new evidence does not backfill historical receipts.

## Coordinated features

| Change | Boundary |
| --- | --- |
| Explicit access-token resource audience | Separate from Sandhi's introspection client and browser ID-token audience |
| Typed output reasoning | Chat contract minor 14; Rust output struct literals supply `reasoning: None` or `Some(...)`; wire schema v1 remains unchanged |
| Explicit compatible endpoint profiles | Provider labels and catalog aliases do not confer endpoint authority or usage semantics |
| Dashboard access states | Shared starter access, protected operator token and OIDC permissions remain distinct; mint controls follow the inference profile |
| Authenticated transport | Standalone credential-bearing listeners require TLS; explicit HTTP exceptions are limited to literal loopback |
| Release-feature preflight | Public Linux and macOS builds run actual binary lifecycle checks before tagging; this alone is not ONNX model execution acceptance |

Follow the [protocol and evidence matrix](../product/protocol-and-credential-matrix.md),
[cache and token guide](../product/cache-aware-routing.md), and
[local ONNX egress controls](../operator/embedded-onnx.md). Token units and reporting
coverage do not imply provider billing equivalence, cache hits or monetary savings.

## Identity dependency order

The [Anvai Identity integration guide](../operator/oidc-sso.md) tracks local
acceptance separately from the public development issuer. Qualify the IDM artifact,
schema, advertised contract and dedicated registrations first; then qualify Sandhi
and Victor against that contract. The public development route retains
authentication. No production issuer or tenant cutover is part of this train.

Release order is **Sandhi → verified official SDK → Victor**. Required public
platform CI, exact committed review and all-target publication verification remain
release gates. See the [progress ledger](../reviews/post-0.17.0-pr-train.md).
