= Sandhi Proxy — Operator Guide
:toc: left
:toclevels: 3
:sectnums:
:icons: font
:docinfo: shared
//:source-highlighter: rouge   # GitHub applies its own; harmless elsewhere

This guide walks an operator through running Sandhi as an **inline reverse-proxy** and
pointing a client — Victor, or any vendor SDK — at it, so every model call is counted and
attributed while the real upstream key never leaves the server.

*Audience:* anyone deploying Sandhi for a team that shares one upstream key.
*Scope:* the proxy shape (cross-process / shared-key). For the in-process binding shape
(same process, no network hop) see the README's _Two shapes, one core_.

[NOTE]
====
Sandhi emits **neutral units only** (tokens, the cache-creation/read split, GPU-seconds).
Pricing, billing, and tier policy are downstream concerns owned by the AnvaiOps control
plane — nothing here involves dollars.
====


== How it fits

The 0.18 source candidate defaults to a credential-free loopback starter with
one shared identity and budget. Tokens and OIDC are optional profiles. Follow
link:oidc-sso.md[access profiles and Anvai Identity integration]
for browser login, role assignment and short-lived agent access tokens. The virtual-key
bootstrap examples below require explicitly selecting `SANDHI_AUTH_MODE=tokens`; they do not
override an OIDC failure or grant access to an OIDC deployment.

In the token profile below, Sandhi sits between your callers and the real provider. Callers authenticate with a
per-user *virtual key*; Sandhi holds the *real* upstream key server-side, forwards the
request, meters it as the bytes pass through, and reconciles the caller's budget.

[literal]
....
  +----------+     Bearer vk_alice     +-----------------+     real key     +-----------+
  |  Client  | ----------------------> |  Sandhi proxy   | ---------------> |  Upstream |
  | (Victor /|        (virtual key)    |    :8787        |   (held server-  | (Anthropic|
  |   SDK)   | <---------------------- |  meters in-path | <--------------- |  / OpenAI)|
  +----------+     response bytes      +-----------------+     response     +-----------+
                                          |  ^
                                          v  |  UsageEvent (tokens + cache split)
                                       +-----------------+
                                       |  original DB    |   required durable paired execution + observations
                                       +-----------------+
....

The client never sees the real key. Attribution (`subject_id` / `group_id` / `session_id`)
rides in metadata *outside* the cached prompt, so hosted prompt caches keep hitting and
self-hosted KV routing stays sticky.


== The operator mental model: credential, virtual key, budget

Three objects, configured in that order. Two are server-side secrets; one is what you hand
to a caller.

[literal]
....
  1. register once               2. mint per user                  3. enforce
  +----------------+             +----------------+                 +----------------+
  |  CREDENTIAL    |  upstream   |  VIRTUAL KEY   |   budget_scope  |   BUDGET       |
  |  anthropic:    |   _ref      |  vk_alice      |   ------------> |  group:platform|
  |    default     | <---------. |  subject=alice |                 |  limit=1M tok  |
  |  sk-ant-XXXX   |            | | rate=60/min   |                 |  window=monthly|
  |  (in the vault)|            | | (stored hash) |                 |  policy=block  |
  +----------------+            | +----------------+                 +----------------+
        |  real key + base_url   |
        |  rehydrated into a     |   The vkey carries ONLY upstream_ref (provider:label),
        |  ProviderHandle at     |   never the secret. Lose the vkey? Revoke + re-mint.
        |  startup; never sent   |
        |  to the client.        |
....

[NOTE]
====
The binding between a virtual key and its upstream is the **credential id** `provider:label`
(e.g. `anthropic:default`). The real key and base URL live in the vault under that id; the
virtual key references it by name only.
====


== Prerequisites

* A built Sandhi workspace — the first `cargo run` compiles (~1–2 min).
* A real upstream key to put in the vault (e.g. an Anthropic `sk-ant-…`).
* For the Victor client path: Victor installed with its `sandhi` extra
  (`pip install -e '.[sandhi]'`), which pulls the `sandhi-gateway` FFI wheel.


== Step 1 — start the proxy

Serving configuration comes from environment/configuration files. Informational `--help`
and `--version` do not initialize stores. HTTP generation requires the original ordinary
SQLite file and one ledger shard; remove the obsolete accounting variable before startup.
The following is explicit local token bootstrap, not an OIDC bypass. For an upgrade,
quiesce old writers and retain the original file/caps/holds first; follow
link:../releases/v0.17.0.md[the 0.17.0 migration checklist].

[source,bash]
----
unset SANDHI_BUFFERED_ACCOUNTING
SANDHI_AUTH_MODE=tokens \
SANDHI_LEDGER_SHARDS=1 \
SANDHI_STORE=usage.db \
SANDHI_ADMIN_TOKEN=admin-secret \
cargo run -p sandhi-proxy --bin sandhi-proxy
----

On startup it prints (to stderr):

[literal]
....
sandhi-proxy listening on http://127.0.0.1:8787  (OpenAI Chat/Responses | Anthropic Messages | Gemini, virtual-key auth)
....

[start=2] .Startup environment
|===
| Variable | Default | Effect

| `SANDHI_BIND`
| `127.0.0.1:8787`
| Listen socket. Must parse as a `SocketAddr`. When `tls` is configured this socket serves `https://`.

| `SANDHI_HTTP_BIND`
| _(unset → no plaintext listener)_
| Optional second, **plaintext** HTTP listener served by the same process. Authenticated profiles refuse it unless `SANDHI_ALLOW_LOOPBACK_HTTP=1` and this socket is loopback. Requires listener TLS (`tls.cert`/`tls.key`; without it the `SANDHI_BIND` socket is already plaintext, so setting this fails startup) and must differ from `SANDHI_BIND`. Both sockets share one admission budget, one per-IP table, and one graceful drain. Credential-bearing modes never permit a non-loopback plaintext socket.

| `SANDHI_ALLOW_LOOPBACK_HTTP`
| `0` (also when unset)
| Exact `1` deliberately permits loopback-only HTTP for tests or same-host TLS termination. Tokens, OIDC, optional admin tokens and client-credentials registries otherwise require listener TLS with no plaintext companion. Other values fail startup. This never admits wildcard, LAN or IPv4-mapped IPv6 sockets; forwarding headers do not prove TLS.

| `SANDHI_CONFIG`
| _(unset)_
| Declarative JSON configuration. Optional `tls.cert` / `tls.key` enable listener TLS. Optional `buffered_deadlines` configures global, credential-endpoint and exact-model buffered limits; see link:buffered-deadlines.md[buffered deadlines]. Optional `streaming_deadlines` configures complete setup/idle/body limits per authorized route; see link:streaming-deadlines.md[streaming deadlines]. Without a streaming override the source defaults are setup 30 s / idle 90 s / body 180 s, under a 240 s ceiling. These sections require restart; invalid startup configuration fails before bind.

| `SANDHI_STORE`
| _required_
| Original ordinary SQLite file. Committed usage, vkeys, budgets, paired execution and reference proofs survive restart; best-effort observations remain separate. Absent/empty paths, `:memory:` and SQLite `file:` URIs refuse startup before stores open. Storage initialization failures exit `2` before binding. Preserve the existing file and complete recovery state; there is no development memory-serving fallback.

| `SANDHI_LEDGER_SHARDS`
| `1`
| Must be unset or exactly `1` for serving. Other values refuse before ledger open/migration. Legacy multi-shard snapshots require explicit offline migration; this is not a contention-tuning switch.

| `SANDHI_BUFFERED_ACCOUNTING`
| _removed; must be unset_
| Any supplied value, including `tracked` or `off`, refuses startup. All generation uses one paired durable owner; provider FFI remains ledger-free.

| `SANDHI_DEFAULT_MAX_OUTPUT_TOKENS`
| `4096`
| Operator-owned missing-chat-limit default (positive integer up to 1,000,000); a declared model ceiling can narrow it. Explicit caller limits stay explicit. This is an admission estimate, not a universal physical bound; constrained Codex keeps its codec's omitted wire maximum. Native Text Completions defaults to `16`; Embeddings is input-only.

| `SANDHI_ADMIN_TOKEN`
| _(unset → admin API disabled)_
| The admin bearer. **Setting it enables `/admin/*`** and (by default) gates dashboard data APIs and `/metrics`. The dashboard HTML shell is public; data is authenticated separately.

| `SANDHI_PUBLIC_URL`
| `http://localhost:8787` (`https://...` when TLS is configured)
| Externally-reachable URL returned to callers when a vkey is minted. Set explicitly when the public host/port differs from the listener.

| `SANDHI_VAULT_BACKEND`
| `keyring`
| Secret backend: `keyring` (OS keychain) or `sentinelpass`. Native IPC requires the `sentinelpass-ipc` feature and configured tokens. Missing support/configuration or unknown names leave the vault unavailable; no automatic fallback.

| `SANDHI_OPENAI_KEY` / `SANDHI_ANTHROPIC_KEY` / `SANDHI_GEMINI_KEY`
| _(unset)_
| Demo environment bootstrap: transient upstream/`vk_*_demo` credential handles without the operator vault. The required original durable execution ledger is unchanged; prefer Steps 2–4 for persistent credential management.

| `SANDHI_OPENAI_BASE` / `SANDHI_ANTHROPIC_BASE` / `SANDHI_GEMINI_BASE`
| provider default
| Optional base-URL overrides for the corresponding legacy demo bootstrap only.

| `SANDHI_DASHBOARD_PUBLIC`
| _(unset → false)_
| Set to exactly `1` to open `/dashboard` + `/metrics` without the admin token.

| `SANDHI_ERROR_DETAIL`
| _(unset → redacted)_
| Set to exactly `full` to surface full upstream errors to clients. Default redacts to code/status/request-id; server logs always carry the full error.

| `SANDHI_METRICS_MAX_SERIES`
| `1024`
| Maximum distinct bounded-label metric series. New series beyond the cap fold into a shared `(overflow)` model while totals remain exact. Raise only for a genuinely larger model fleet.

| `SANDHI_MAX_REQUEST_BODY_BYTES`
| `2097152` (2 MiB)
| Maximum request body buffered; AI ingress routes return their dialect-shaped `413` when exceeded. Raise deliberately for inline multimodal payloads (for example, `33554432` for 32 MiB). Application-owned request-body memory is bounded by this value multiplied by `SANDHI_MAX_IN_FLIGHT_AI_REQUESTS`.

| `SANDHI_MAX_IN_FLIGHT_AI_REQUESTS`
| `128`
| Maximum AI requests admitted concurrently to body extraction and dispatch; the slot is held for the whole response (streaming included), so this bounds simultaneously open model streams. Waiting calls remain outside the application body buffer; health, metrics, discovery, and admin routes do not consume this pool.

| `SANDHI_MAX_CONNECTIONS`
| `1024`
| Maximum concurrent TCP connections. Connections beyond the cap are closed without a response (the AI admission path is where dialect-shaped shedding happens). Connections cannot spend their whole lifetime silent — see `SANDHI_HEADER_READ_TIMEOUT_SECS`.

| `SANDHI_MAX_CONNECTIONS_PER_IP`
| `0` (disabled)
| Maximum concurrent TCP connections from one peer IP. **Off by default because it counts the peer at accept time**: behind a load balancer or NAT every connection shares one IP, and a default-on cap would shed the balancer's connections. Enable it when the proxy is directly exposed, or after configuring `SANDHI_TRUSTED_PROXIES` so request-level client resolution works.

| `SANDHI_HEADER_READ_TIMEOUT_SECS`
| `30`
| Seconds a connection may take to transmit its complete request head; slowloris-style partial heads are closed at the deadline. A connection that sends nothing at all is closed by the same timer. Once the head is complete the timer stops — streaming responses are not killed by it.

| `SANDHI_TRUSTED_PROXIES`
| _(unset → trust no one)_
| Comma-separated CIDR allowlist (for example `10.0.0.0/8,192.168.1.0/24`). `X-Forwarded-For` is believed only when the connection's peer is in this list; anything else is treated as the client. Never enable forwarding headers from peers you do not control.

| `SANDHI_USAGE_BUFFER_CAPACITY`
| `1024`
| Bounded background queue for durable usage-event writes. A full queue drops and counts new observational events instead of blocking model responses or growing without bound; accepted events drain during graceful shutdown.

| `SANDHI_ALERT_BUFFER_CAPACITY`
| `256`
| Bounded background queue for persisting alert `last_fired_at` dedup state. Live alert evaluation remains immediate; persistence drains during graceful shutdown.

| `SANDHI_SHUTDOWN_GRACE_SECS`
| `30`
| One total deadline after observed SIGINT/SIGTERM, including quiesce, connections, accounting, writer drains, telemetry and runtime teardown. The binary exits `124` when cleanup remains incomplete; settlement/persistence is not guaranteed after forced exit.

| `SANDHI_SHUTDOWN_QUIESCE_MS`
| `1000`
| Nonnegative same-port probe window after cutoff; clamped to one quarter of the remaining shutdown grace so drain retains time. `0` closes admission to new connections immediately. The window consumes the original grace, not an additional timeout.

| `SANDHI_REPLICA_COUNT`
| `1`
| Declared deployment topology. Values greater than `1` fail startup because the shipped enforcement ledger and rate limiter are single-node; this prevents an apparently valid multi-replica deployment from weakening hard caps or multiplying rate limits.

| `SANDHI_LOG` (or `RUST_LOG`)
| `sandhi_proxy=info,…`
| tracing filter; logs go to stderr.

| `SANDHI_OTEL_EXPORT`
| _(unset → off)_
| OTLP export (TD-0011 P3, requires the `otel-otlp` cargo feature). Set to exactly `otlp` to push `gen_ai.*` spans + metrics to a collector; unset behaves like the default build. See also `SANDHI_OTEL_ENDPOINT` / `SANDHI_OTEL_PROTOCOL` (default `http://localhost:4318` / `http/protobuf`).
|===

[CAUTION]
====
Serving uses the original single-file paired ledger. Do not change shard count, substitute
an empty database or delete evidence to bypass refusal. Quiesce older writers, preserve the
complete snapshot and plan any legacy topology conversion offline. Historical caps, settled
spend, live holds, dedup history and compatible route pins remain authoritative.

Qualified source evidence and one physical attempt commit before an original paired receipt;
usage events and dashboard observations are not those receipts. Unknown usage remains held
through expiry/restart, while historical unpaired TTL semantics stay separate. Native-reference
proofs also initialize on this same file; no separate registry setup or second ledger is needed.
See link:buffered-accounting.md[durable execution] and
link:backends.md#native-reference-ownership[native ownership] for the supported boundaries.
====

When `SANDHI_VAULT_BACKEND=sentinelpass`, native IPC reads `SENTINELPASS_CLIENT_TOKEN`,
`SANDHI_SENTINELPASS_CLIENT_ID` (default `sandhi`), and `SANDHI_SENTINELPASS_SOCKET`. Set
`SANDHI_SENTINELPASS_TOKEN_FILE` to use an explicit private daemon-token file (for example in a
container). An invalid or empty explicit file fails configuration; it never falls back to the
user's platform configuration directory. Without this option the protocol's existing default
token location is unchanged. Set
`SANDHI_SENTINELPASS_FALLBACK_CLI=1` to force the legacy CLI backend; its executable override is
`SANDHI_SENTINELPASS_BIN` (default `sentinelpass`). Native IPC is enabled in release binaries and in
source builds made with `--features sentinelpass-ipc`.

Native IPC now requires a SentinelPass daemon compatible with protocol 0.13.3 secured sessions.
On Windows the transport uses named pipes; the former `tcp://` loopback transport is unsupported.
On Unix the socket parent must be owned by the current user, owner-only (0700), and not a symlink.
Upgrade the daemon before the client; preserve the prior binaries/configuration for rollback.
A handshake, authentication or permission failure is explicit: there is no automatic plaintext
or CLI retry. The daemon token and per-client grant remain separate credentials.

Native IPC uses a dedicated runtime thread and a bounded queue. Its default deadline is 5000 ms,
including queue time; `SANDHI_SENTINELPASS_TIMEOUT_MS` accepts 50–30000 ms. A timed-out write may
have applied in the broker: reconcile before retrying. The explicit legacy CLI backend has no
I/O deadline and is disabled for interactive reference onboarding.

For read-only runtime grants, provision through the broker first, then use
`sandhi keys reference openai default` or the dashboard's “Existing reference (read-only)” mode.
`POST /admin/keys/reference` never writes a secret. `GET /admin/version` reports local backend
operations separately from grants (`grant_status: not_checked`). Local credential revocation
does not revoke a broker grant or provider key, and reports secret cleanup separately.
See link:../product/broker-integration-contract.md[the broker contract] for setup, failure codes,
partial-write recovery, canonical references and the remaining live-daemon gates.

[IMPORTANT]
====
Without `SANDHI_ADMIN_TOKEN`, every `/admin/*` call returns **403** and you cannot provision
keys. Set it now — steps 2–4 depend on it.
====

[CAUTION]
====
Authenticated standalone listeners require TLS. Only explicit `SANDHI_ALLOW_LOOPBACK_HTTP=1`
permits loopback HTTP for disposable tests or a same-host TLS terminator. LAN and wildcard
plaintext sockets are refused even with that exception. The credential-free starter is unchanged.
====

=== Optional listener TLS

TLS is configured declaratively by path; the private-key bytes do not belong in the JSON file:

[source,json]
----
{
  "tls": {
    "cert": "/run/sandhi/tls/fullchain.pem",
    "key": "/run/sandhi/tls/privkey.pem"
  },
  "providers": [],
  "budgets": [],
  "alerts": [],
  "vkeys": []
}
----

[source,bash]
----
SANDHI_CONFIG=/etc/sandhi/config.json \
SANDHI_BIND=0.0.0.0:8787 \
cargo run -p sandhi-proxy --bin sandhi-proxy
----

The certificate file may contain a leaf-first chain. The key may be PKCS#1, PKCS#8, or SEC1 PEM.
Sandhi validates the complete pair before accepting traffic and serves `https://` when it is valid;
an incomplete, unreadable, malformed, or mismatched pair fails startup. Without the `tls` object,
only the credential-free starter or the explicit loopback exception may serve HTTP. Certificate reload without interrupting existing
streams is tracked separately; restart the process to replace the identity in this phase.

==== Upgrade credential-bearing HTTP deployments

Earlier sources warned about plaintext listeners. The 0.18 candidate now refuses them by
default for token/OIDC mode, an optional admin token, or a client-credentials registry.
Configure `tls.cert`/`tls.key`, remove `SANDHI_HTTP_BIND`, and update clients to the verified
HTTPS URL before restarting. Do not disable authentication to restore an old HTTP route.
For same-host TLS termination only, bind the backend to `127.0.0.1` or `::1` and explicitly
set `SANDHI_ALLOW_LOOPBACK_HTTP=1`; keep client-facing HTTPS and access controls at the terminator.
An HTTP hop over the LAN is not eligible for the exception.

==== Dual-scheme serving: HTTP and HTTPS in one process

With TLS enabled, `SANDHI_HTTP_BIND` opens a second, **plaintext** listener alongside it — for
explicit loopback tests or a same-host TLS terminator:

[source,bash]
----
SANDHI_CONFIG=/etc/sandhi/config.json \
SANDHI_BIND=0.0.0.0:18788 \
SANDHI_HTTP_BIND=127.0.0.1:18789 \
SANDHI_ALLOW_LOOPBACK_HTTP=1 \
cargo run -p sandhi-proxy --bin sandhi-proxy
----

The TLS listener keeps `SANDHI_BIND`; the plaintext companion takes its own socket. Both bind
before either accepts traffic, and they share one process-wide admission budget, one per-IP
connection table, and one graceful drain — the connection caps (TD-0014 P3) bound the process,
not the port. Each scheme is disabled by the absence of its setting: no `tls` object → HTTP only;
no `SANDHI_HTTP_BIND` → HTTPS only. Same-port protocol multiplexing is deliberately not offered;
see TD-0017 D7.

[CAUTION]
====
Virtual keys are bearer credentials. Authenticated modes refuse every non-loopback plaintext
companion. An explicit loopback exception does not authenticate a forwarding proxy or prevent
other local processes from connecting; protect that local boundary separately.
====

=== Optional reviewed desired state

The same `SANDHI_CONFIG` file can declare providers, budgets, alerts, and virtual-key intent. It is
not applied automatically at startup: preview it with `GET /admin/config`, then apply it explicitly
with `POST /admin/config/apply`. Apply is additive-only — it creates or updates declared objects but
never revokes an object merely because it disappeared from the file.

[source,json]
----
{
  "providers": [
    {
      "provider": "anthropic",
      "label": "default",
      "scheme": "api-key",
      "secret_env": "ANTHROPIC_API_KEY"
    }
  ],
  "budgets": [
    {
      "scope": "group:platform",
      "limit_tokens": 1000000,
      "window": "monthly",
      "policy": "block",
      "alert_thresholds": [80, 100]
    }
  ],
  "alerts": [],
  "vkeys": [
    {
      "upstream": "anthropic:default",
      "subject": "alice",
      "group": "platform",
      "models": ["claude-sonnet-5"],
      "rate_limit_per_min": 60
    }
  ]
}
----

Provider secrets and webhook URLs never belong in the file; `secret_env` and `webhook_env` name
variables in the proxy process. An absent or unset provider secret resolves to a keyless provider,
so verify named variables before apply. A newly minted virtual key appears in the apply response
once and must be captured exactly like the Step 3 response. TLS is startup-only: preview/apply
reports `restart required` when `tls` is present.

[source,bash]
----
curl -sS http://localhost:8787/admin/config \
  -H "Authorization: Bearer ${SANDHI_ADMIN_TOKEN}"

curl -sS -X POST http://localhost:8787/admin/config/apply \
  -H "Authorization: Bearer ${SANDHI_ADMIN_TOKEN}"
----

Both routes require the admin bearer in this explicit token-mode example and use the
required original durable `SANDHI_STORE`. Production OIDC authorization remains unchanged. Use the manual CLI flow below when a virtual key needs an explicit budget scope,
expiry, or another field not represented by the desired-state `vkeys[]` entry.

=== Management commit and failure semantics

Budget admission is estimate-based, even with `policy: block`: bytes/4 is not a proven input
token bound, and every in-flight call can contribute excess. No provider/model currently has a
strict total-token-cap guarantee. See link:../product/metering-and-budget-guarantees.md[the
metering and budget matrix] for controls, missing proofs, reasoning semantics and upgrade rules.

`POST /admin/budget` validates a nonempty scope, a `total`/`daily`/`monthly` window, a
`block`/`warn` policy, a limit from zero through `9223372036854775807`, and any alert thresholds
from zero through 100. Unknown spellings are errors, not fallback policy choices. A rejected
budget request returns 400 before writing. Config apply validates all declared budget and alert
intent before touching any backend. Other component errors are reported as apply failures.

Budget persistence on the required original `SANDHI_STORE` must succeed before live metadata
changes or the API acknowledges the update. A failed budget commit returns 503 and leaves the previous policy
unchanged. Concurrent budget updates are serialized through commit/publication; the final live
policy matches durable state. This is last-writer-wins, not revision/ETag conflict detection.
Missing storage refuses serving; `Warn` may exceed a soft cap but never admits generation
through a storage failure. Unknown paired usage remains held beyond TTL until qualified
settlement or valid pre-dispatch closure; it is not a timer-based zero.

[IMPORTANT]
====
Config apply and a budget with inline alerts are *not* multi-store transactions. HTTP 503 does
not necessarily mean that nothing changed. Inspect the JSON response before retrying:

* Config: `ok: false`, an `error` summary, a `failures` array identifying failed components,
  and the usual `providers.applied`, `budgets.applied`, `alerts.created/skipped` and
  `vkeys.minted/skipped` lists. Committed items are not rolled back. A failed budget's inline
  alerts are not attempted. A failed inventory read is a failure, not a successful skip.
* Budget with inline alerts: `budget_applied: true` means the budget committed even if some
  alerts failed; `alerts_created` and `alerts_failed` report the outcome. If the alert store is
  absent, the request is rejected before the budget changes.
* The dashboard renders incomplete config results and still shows keys minted in that response.
  Copy them before another apply or clearing authentication. The CLI prints partial budget
  results and exits nonzero. Direct API consumers must preserve the response body on errors.
====

After a failure, compare inventory and the committed-item lists, repair the failing backend or
intent, then apply deliberately. Sequential config retries deduplicate satisfied alerts and key
identities; direct budget alert creation can duplicate rules on retry. Concurrent config apply
is not an exactly-once workflow, and no automatic retry/rollback guarantee is implied. Shared
policy revisions and transactional multi-store reconciliation remain future work.


== Step 2 — register the real upstream credential

In a second shell, use the `sandhi` operator CLI (a thin client to the admin API):

The CLI defaults to `http://localhost:8787`; set `--admin-url` or `SANDHI_ADMIN_URL` when the
admin endpoint is elsewhere. `--admin-token` can likewise come from `SANDHI_ADMIN_TOKEN`.

[source,bash]
----
# Pipe the secret via stdin so it never appears in shell history:
printf '%s' 'sk-ant-xxxxxxxx' | cargo run -p sandhi-proxy --bin sandhi -- \
  --admin-token admin-secret \
  keys add anthropic default --base-url https://api.anthropic.com
----

This stores the key in the vault under credential id **`anthropic:default`** and caches a
`ProviderHandle` (key + base URL baked in) ready to serve.

`keys add` reference:
[cols="1,3"]
|===
| `keys add <provider> [label]` | Registers `provider:label`. `label` defaults to `default`.
| `--base-url <URL>` | Upstream API base. Optional — per-provider defaults apply (e.g. `https://api.anthropic.com`).
| `--secret <SECRET>` | The real key. Omit and pipe one line via stdin to keep it out of history.
| `--scheme api-key\|bearer\|oauth` | Credential scheme. Optional — inferred from the provider.
|===

[TIP]
====
`keys list` shows registered credentials; `keys revoke <provider> <label>` removes one.
====

[TIP]
====
**Self-hosted InferFlux** (ADR-0008) is a first-class OpenAI-compat slug with the default base
`http://127.0.0.1:8080/v1`, so registration needs no `--base-url` on a default install:

```bash
# Keyless local server (InferFlux serves anonymous read+generate when no keys are configured):
printf '\n' | cargo run -p sandhi-proxy --bin sandhi -- --admin-token admin-secret \
  keys add inferflux default
# Secured deployment: pipe the real key the same way as any provider.
```

Model ids are whatever you loaded in InferFlux's own `registry.yaml` — mint the vkey
`--models` list against those. If the server runs with
`runtime.scheduler.session_handles.enabled: true`, Sandhi's `x-sandhi-session` request header
is mapped onto InferFlux's `x-inferflux-session-id` KV/prefix-cache affinity automatically.
====


== Step 3 — mint a virtual key

[source,bash]
----
cargo run -p sandhi-proxy --bin sandhi -- --admin-token admin-secret \
  keys share anthropic:default \
    --subject alice --group platform \
    --budget group:platform \
    --models "claude-sonnet-5,claude-haiku-4-5" \
    --rate 60
----

The response prints the plaintext key **once**:

[source,json]
----
{
  "virtual_key": "vk_3Kp9...mQ",        // <-- COPY NOW; irretrievable afterwards
  "id": "key_01HK...",
  "upstream_ref": "anthropic:default",
  "endpoint": "http://localhost:8787/v1/messages",
  "auth": "Authorization: Bearer vk_3Kp9...mQ"
}
----

`keys share` reference:
[cols="1,3"]
|===
| `--subject <id>` | Who this key attributes spend to.
| `--group <id>` | Team; budgets pool at the group when set.
| `--budget <scope>` | Budget scope to bind (e.g. `group:platform` or `vk:<id>`).
| `--models "a,b"` | Comma-separated **model allowlist**; calls for other models are refused.
| `--rate <n>` | Per-minute request limit for this key.
| `--expires <RFC3339>` | Optional expiry; expired keys are rejected at resolve time.
|===

[WARNING]
====
The virtual key is shown **only at mint time**. Sandhi stores a SHA-256 hash, not the
plaintext — if you lose it, `vkeys revoke <id>` the old one and mint a new one.
====

[NOTE]
====
Per-minute rate limits are held **in-memory**, and SQLite budget enforcement is durable but
single-node. The binary refuses `SANDHI_REPLICA_COUNT > 1`; deploy one proxy replica until a
shared backend satisfies the enforcement conformance suite.
====


== Step 4 — set a budget

[source,bash]
----
cargo run -p sandhi-proxy --bin sandhi -- --admin-token admin-secret \
  budget set group:platform 1000000 --window monthly --policy block --alert 80 --alert 100
----

* `--window total|daily|monthly` — spend is measured over calendar-aligned windows.
* `--policy block|warn` — `block` refuses calls past the cap; `warn` is a soft cap that
  admits over the limit but still tracks spend (for alerts).
* `--alert <pct>` — repeatable; each value creates a log-channel alert rule at that % of the limit.

Inspect with `budget list`, `budget usage group:platform`.

  -H 'Content-Type: application/json' \

Victor has a first-class gateway mode (TD-0003 P3). In `~/.victor/profiles.yaml`:

      url: http://localhost:8787          # the Sandhi proxy

  #   gateway:
  #     url: http://localhost:8787

This builds the Sandhi FFI handle with `base_url=proxy`, `api_key=virtual_key`, and

| Virtual key via | Works? | Notes

| env `SANDHI_GATEWAY_VIRTUAL_KEY`

== Step 7 — observe the metering

[source,bash]
----
# Spend attributed per subject
cargo run -p sandhi-proxy --bin sandhi -- --admin-token admin-secret usage --by subject

# Budget burn-down for a scope
cargo run -p sandhi-proxy --bin sandhi -- --admin-token admin-secret budget usage group:platform

# Masked virtual-key inventory
cargo run -p sandhi-proxy --bin sandhi -- --admin-token admin-secret vkeys list

* **Dashboard:** Open `http://localhost:8787/dashboard`, enter the admin token and select
  *Use token* (or press Enter). The public HTML shell and compiled CSS/JavaScript assets need
  no separate frontend server. Data reads attach the bearer unless public access is enabled;
  mutations, config previews and run lookups always require admin access. Inventory values
  are masked; newly minted keys are shown once for copying.
  The token stays in page memory, not browser storage. Editing or clearing it immediately
  clears privileged panels and one-time results. Reloading requires re-entry. Management
  responses use `Cache-Control: no-store`; use HTTPS beyond a trusted local hop.
  Panels distinguish authentication/permission errors, unconfigured stores and unavailable
  data. A failed refresh retains prior data only with a *stale* label and timestamp; it is not
  a fresh zero-usage report. Storage read failures return 503. Public access exposes data
  deliberately and should not be enabled just to work around authentication.
* **Metrics:** `GET /metrics` (Prometheus text), gated the same way. See the
  observability section below for the four alerts worth wiring.


== Observability and telemetry

=== Readiness and shutdown

Use unauthenticated `GET /readyz` for traffic readiness (`200` while running, `503` after
shutdown cutoff; `Cache-Control: no-store`). `GET /healthz` remains process liveness (`200`).
Readiness describes drain state only, not provider, ledger, vault or writer health. Migrate
traffic probes from `/healthz` to `/readyz`; retain `/healthz` for liveness checks.

At cutoff, queued and newly arriving AI requests return dialect-shaped `503` with
`Retry-After: 1` (`gateway_draining`, or Gemini `UNAVAILABLE`). Body uploads that span cutoff
cannot authorize model dispatch afterward. Authenticated admin mutations also return `503`;
a multi-item config apply may have already committed earlier items, so inspect its partial
results before retrying. Read-only operations remain available during quiesce.

During the bounded quiesce window, fresh HTTP/TLS connections and existing keep-alive
connections can probe the same port. Global/per-IP connection limits still apply: saturated
connections may be shed before HTTP and no reserved probe capacity is promised. Size the
window and external traffic-drain timing for your deployment. After quiesce the listener
closes and existing connections drain; fresh probes are no longer reachable.

Cutoff serializes *dispatch authorization*, not the instant bytes reach an upstream. Already
authorized work may finish during drain. Abandoned, undispatched reservations are rolled back
without usage events; admitted streams retain accounting ownership through finalization.
One monotonic deadline covers all phases. Normal cleanup exits `0`; deadline/incomplete
cleanup exits `124`, possibly leaving uncertain settlement or best-effort observations.
Do not interpret timeout as a successful flush or retry an uncertain model call blindly.
The process watchdog does not depend on Tokio cancellation and does not log on its hard-exit
path. See link:recovery-drill.md[the isolated recovery rehearsal] for fixed-topology snapshots,
crash liabilities and revocation reconciliation. Physical-attempt evidence and paired receipts
are part of the required owner; best-effort telemetry remains separate. Native-reference proof
workers retain lifecycle ownership through queue residence, mutex/SQLite waits and completion;
they share the original request/response and earlier shutdown deadline, without a fresh window.

Library embedders retain runtime ownership: deadline expiry requests cancellation and returns
`io::ErrorKind::TimedOut`, rather than forcing process termination. Synchronous destructors
or blocking tasks may continue; embedders must supply their own process-level termination
policy if a hard bound is required.

=== Logs

`SANDHI_LOG` (falling back to `RUST_LOG`) controls the tracing filter; logs go to stderr. The
default keeps admission/accounting failures and bounded recovery/shutdown diagnostics
without per-request chatter. `SANDHI_LOG=debug` adds plane selection per call.

=== Prometheus metrics

`GET /metrics` is gated by the same admin bearer as the dashboard when
`SANDHI_ADMIN_TOKEN` is set:

[source,yaml]
----
scrape_configs:
  - job_name: sandhi
    metrics_path: /metrics
    authorization: { credentials: "<SANDHI_ADMIN_TOKEN>" }
    static_configs: [{ targets: ["sandhi:8787"] }]
----

Omit `authorization` only when no admin token is configured or the endpoint was deliberately
opened with `SANDHI_DASHBOARD_PUBLIC=1`. Metrics describe the gateway, not individual callers.
Label dimensions are closed, and distinct series are capped by `SANDHI_METRICS_MAX_SERIES`; new
model values beyond the cap fold into `(overflow)` without losing totals. Per-subject attribution
belongs in the bounded usage aggregate instead of metric labels.

Best-effort usage and alert writers expose fixed `buffer="usage"` and `buffer="alerts"` samples:
`sandhi_buffer_configured` is `1` when an observer is attached and `0` otherwise. Unconfigured
buffers omit depth/drop samples; zero must not imply an active healthy writer. Configured
buffers expose `sandhi_buffer_capacity`, `sandhi_buffer_queued`, `sandhi_buffer_in_flight` and
`sandhi_buffer_dropped_total`. Drops include rejected enqueue attempts and queued callbacks
abandoned after worker panic, not the unknown result of the panicking callback itself.
Queued excludes the executing callback and flush/shutdown control
messages, though those control messages share channel capacity. An in-flight callback is not
evidence of a successful database commit. Counters reset on restart; configured is not a worker
liveness check. These metrics follow the existing `/metrics` bearer/public-read policy.

Investigate sustained queue growth or `increase(sandhi_buffer_dropped_total[5m]) > 0` as loss of
best-effort observation. Do not interpret zero drops as complete accounting: storage insert
failures are separate, and observations are not settlement receipts. The former standalone
memory-ring mode is not a serving option. These are not
W05 settlement-outbox backlog metrics. The new buffer signals are Prometheus-only; OTLP parity,
oldest-item age remain tracked follow-ups. Offline backup/restore rehearsals are covered by
link:recovery-drill.md[W06c]; online/fleet recovery is not implied.

Unlabelled `sandhi_ready`, `sandhi_shutdown_active_operations` and
`sandhi_shutdown_elapsed_seconds` follow the same metrics authorization. Active operations
counts tracked model/reservation/admin work and retained native-reference metadata workers,
including workers queued for the blocking pool or waiting on storage. It does not count every
unadmitted queued HTTP request or connection and does not prove a durable commit.
Elapsed time is zero before cutoff; metrics are scrapeable only while their
connection remains reachable. Drain progress logs report active connections/operations and
remaining time; these signals do not confirm persistence.

[cols="2,3,5"]
|===
| Alert | Expression | Why

| Capacity leaking
| `increase(sandhi_settle_failures_total[15m]) > 0`
| Inspect the original receipt and retained liability. Unknown paired usage survives TTL/restart; expiry is not zero usage. This retained counter alone does not cover all current owner failures.

| Unexpected legacy unmetered signal
| `increase(sandhi_admitted_unmetered_total[15m]) > 0`
| Retained compatibility counter; current paired HTTP has no ledger-error fail-open path, including Warn. Investigate a nonzero legacy/exporter signal; do not select it as an operating mode.

| Callers being refused
| `rate(sandhi_reservations_denied_total{policy="block"}[5m]) > 0`
| Distinguishes exhausted caps from upstream failures.

| Upstream degrading
| `histogram_quantile(0.95, rate(sandhi_request_duration_ms_bucket[10m])) > 30000`
| Surfaces a slow provider/model before clients report it.
|===

These retained metric names are not activation switches or complete authoritative accounting
coverage. Their historical HELP text does not authorize fail-open admission or TTL release of
unknown pairs. Zero legacy counters do not establish healthy receipts. A sustained
`sandhi_leases_reclaimed_total` concerns expiry-eligible legacy leases; canonical unknown pairs
remain held. Inspect persisted execution/receipt evidence and accounting diagnostics separately.

=== OTLP export (opt-in)

Build the proxy with `otel-otlp`, then opt in at runtime. The exporter emits one `gen_ai` operation
span per chat call plus token-usage, operation-duration, and time-to-first-token metrics. It runs
beside `/metrics`; both may be enabled. This example uses the guide's explicit local
token bootstrap. Production must retain its approved OIDC/roles/TLS/vault configuration;
enabling export does not change authentication or the original store path.

[source,bash]
----
cargo build -p sandhi-proxy --features otel-otlp

unset SANDHI_BUFFERED_ACCOUNTING
SANDHI_AUTH_MODE=tokens \
SANDHI_LEDGER_SHARDS=1 \
SANDHI_ADMIN_TOKEN=admin-secret \
SANDHI_OTEL_EXPORT=otlp \
SANDHI_OTEL_ENDPOINT=http://otelcol:4318 \
SANDHI_STORE=usage.db \
  cargo run -p sandhi-proxy --features otel-otlp --bin sandhi-proxy
----

[cols="2,2,5"]
|===
| Variable | Default | Purpose
| `SANDHI_OTEL_EXPORT` | _(unset)_ | Set to exactly `otlp` to enable export.
| `SANDHI_OTEL_ENDPOINT` | `http://localhost:4318` | OTLP base URL; the exporter appends `/v1/traces` and `/v1/metrics`.
| `SANDHI_OTEL_PROTOCOL` | `http/protobuf` | `http/protobuf` or `http/json`.
|===

Exported telemetry uses a closed attribute allowlist. It may carry provider, model, operation, and
token counts, but never `subject_id`, `group_id`, `session_id`, `virtual_key_id`, `request_id`, a
credential, or a monetary cost.


== The request lifecycle

What happens to one call, end to end:

[literal]
....
  authenticate      normalize          authorize/admit          source            account/deliver
  ------------      ---------          ---------------          ------            ---------------
  resolve vk    ->  decode caller  ->  model/attribution   ->  dispatch once  ->  source usage/attempt
  select binding    compile cache      rate/default/proof     real credential   original paired receipt
                                        freeze context         observe result    compatible response
                                        reserve both scopes                     best-effort UsageEvent
....

[NOTE]
====
The **reserve ceiling is an admission control, not a cap on the settled total**. A provider
can legitimately report more than was reserved (e.g. a large cache read announced before any
content); Sandhi settles the *real* measured usage and counts the overshoot as a metric
(`sandhi_settle_overshoot_total`) so ceilings can be tuned — it never silently discards a
real measurement.
====


== The two planes (why byte-exact matters)

[literal]
....
  Is the ingress dialect the same family as the upstream?
        |  YES                                  |  NO (cross-family)
        v                                       v
  TRANSPARENT plane                        TRANSLATION plane
  bytes forwarded verbatim                 decode -> ChatRequestV1 -> re-encode
  provider extras survive                  (e.g. /v1/messages -> OpenAI upstream)
  (Anthropic cache_control, etc.)          representable fields/controls preserved
  metered as the stream passes             unsupported meaningful state refuses explicitly
....

Matching endpoint families can preserve compatible native fields, but transparent eligibility
also depends on admitted model/limit/cache changes and credential fences. Missing output limits
can force canonical encoding. Both planes share strict source qualification: native state is
preserved when compatible, otherwise the request/output refuses without silent field loss or
inference replay. Source measurements can settle once even when client delivery fails.
Caller IDs/session hints do not establish native-reference ownership; matching durable source
issuance proof is required before supported continuation. See link:backends.md[backend contracts].

=== Client ingress and authentication

[cols="1,2,2"]
|===
| Route | Dialect | Client auth (the virtual key)

| `POST /v1/chat/completions`
| OpenAI Chat
| `Authorization: Bearer vk_…` (only)

| `POST /v1/responses`
| OpenAI Responses
| `Authorization: Bearer vk_…` (only)

| `POST /v1/messages`
| Anthropic Messages
| `x-api-key: vk_…` (native) *or* `Authorization: Bearer vk_…`

| `POST /v1/models/{m}:generateContent` (also `/v1beta`)
| Gemini
| `x-goog-api-key: vk_…` *or* `Authorization: Bearer vk_…` (the `?key=` query form is refused)

[NOTE]
====
There is **no Cohere ingress** — it is reachable as an *upstream only*, always via the
translation plane. Ollama likewise has no ingress dialect. (Gemini ingress **is** wired —
TD-0010 P4, `POST /v1/models/{model}:generateContent` and its `/v1beta` equivalent.)
====

[NOTE]
====
Both Block and Warn use the caller's explicit output limit or the operator-owned missing-chat
limit default (4096 unless configured, narrowed only by a declared model ceiling). Injection
selects canonical encoding; compatible native controls survive or refuse explicitly. An explicit
provider-native limit keeps transparent eligibility subject to the other model/cache/credential
fences. These are estimates, not strict physical bounds; constrained Codex keeps its codec's
omitted wire maximum. Both planes use original qualified source evidence for one paired receipt;
unknown usage retains both liabilities. Delivery success and observed counters do not prove settlement.
====

[NOTE]
====
**Attribution is key-bound.** The usage event always carries the *virtual key's*
`subject`/`group` (set at mint time). The optional `x-sandhi-subject-id` /
`x-sandhi-group-id` request headers are accepted only when they exactly echo that binding —
any other value (including on a key minted without a subject/group) is refused with a
dialect-shaped **403** before any budget lease. To change attribution, re-mint the key.
====

[NOTE]
====
**Session identity is derived, not required.** An explicit `x-sandhi-session` request
header always wins; otherwise the proxy derives a stable per-conversation key from the
wire body's standard signals — OpenAI `user`, Anthropic `metadata.user_id`, then a hash of
the cacheable system+tools prefix (ADR-0005 D7). A drop-in SDK client therefore gets
session-grouped usage (`sandhi usage --by session`) and vendor cache affinity
(ADR-0008 D3) without any sandhi-specific header.
====

== Troubleshooting

[cols="1,3"]
|===
| Symptom | Cause / fix

| `/admin/*` returns 403
| `SANDHI_ADMIN_TOKEN` not set on the server (Step 1), or the CLI/curl lacks `--admin-token` / `Authorization: Bearer`.

| Client gets 401 / "invalid or missing virtual key"
| Wrong/expired vkey, or wrong header for the dialect (see the auth table). `vkeys revoke` + re-mint if lost.

| "no upstream registered for this key"
| The vkey's `upstream_ref` (`provider:label`) has no matching credential. `keys add` it, or share the correct `provider:label`.

| Calls for a model are refused
| `--models` allowlist on the vkey. Re-mint with the model included, or drop the allowlist.

| 403 "attribution is key-bound"
| The client sent `x-sandhi-subject-id` / `x-sandhi-group-id` that does not match the vkey's
  minted subject/group (or the key was minted without one). Remove the headers, or re-mint
  the key with the intended `--subject`/`--group` — the proxy never adopts client-supplied
  attribution.

| Spend looks doubled
| You turned on Victor's in-process metering (`usage_gateway.enabled`). Leave it off in proxy mode.

| Saved budget/spend is missing after restart
| Check that the exact original `SANDHI_STORE` file was reopened and restored completely. Current serving rejects an unset store; a different empty file is not migration. Quarantine and reconcile the original snapshot rather than recreating caps.
|===

[NOTE]
====
**Contract version skew:** do not infer a contract version from a package version. Query the proxy's
ungated `GET /version` and compare its `wire_contract_version` / `chat_contract_version` with the
binding's `wire_contract_version()` / `chat_contract_version()` result. Both major contracts are
currently `1`; additive chat-contract growth is exposed separately by the bindings' minor counter.
====

[NOTE]
====
Client-facing errors are **redacted by default** (code + status + request id). Set
`SANDHI_ERROR_DETAIL=full` to opt into the full upstream body on the client side; server logs
always carry the full error regardless.
====


== Security notes

* The **real upstream key never leaves the proxy** — it lives in the vault and is rehydrated
  into an in-memory `ProviderHandle` at startup. Clients hold only their virtual key.
* **Protect bearer credentials in transit.** Configure the listener's `tls` block as shown above,
  or terminate TLS at a trusted fronting proxy. Plain HTTP is only for loopback or a trusted hop.
* **Gate the dashboard/metrics** with `SANDHI_ADMIN_TOKEN`; open them only behind a firewall
  or with `SANDHI_DASHBOARD_PUBLIC=1` (values are still masked).
* **Rotate by revoking** — `keys revoke` (credential) and `vkeys revoke` (per-user) are
  immediate; mint replacements with `keys add` / `keys share`.
